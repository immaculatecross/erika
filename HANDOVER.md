> For a new dispatcher session (local or cloud) taking over Erika. Everything the loop needs is in this repo; this file covers only what the other files can't tell you. Read it after `AGENTS.md` and before your playbook.

## Cloud dispatcher sessions — the plumbing differs, the loop doesn't

A dispatcher running in a managed cloud sandbox (e.g. Claude Code on the web) hits three deltas a local checklist won't mention. **(1) No `gh` CLI** — GitHub operations (PRs, reviews, CI state, merges) go through the harness's GitHub tools instead; the review playbook's `gh pr review` becomes: the fresh reviewer session produces the verdict body, and the dispatcher relays it as a PR review/comment and merges on it (the same D-11 single-identity fallback). **(2) The mfactory checkout is not at `../mfactory-v2`** — add the repo through the platform's repo-add mechanism and use wherever it lands; the pinned `.mfactory/` kit here is the fallback if it can't be reached. **(3) Fresh worker/reviewer sessions are spawned via the harness's agent mechanism**, not `claude -p` — same isolation contract (the work order is the worker's entire briefing; the reviewer never sees the builder's reasoning), different invocation. Item 3 of the environment list above ("gh authenticated") reads accordingly in cloud mode. Everything else — boot order, work orders, tiers, pricing, the ritual — is unchanged; the 2026-07-18 mid-RUN-003 handoff ran cold from these files alone.

**Wake discipline on this harness — the hard-won part (RUN-004, three linked lessons).** The loop yields between background units (workers, reviewers, CI) and is re-woken by the harness. The wake channel is unreliable in *both* directions, so never let progress depend on a signal:
- **Act on authoritative durable state; don't wait for a notification.** Every time you're awake — on an agent notification, a fired timer, or an operator turn — poll the *cheap, reliable, durable* signals and take the next real action in the **same turn**: `git ls-remote origin <branch>` answers "did the worker push?"; a minimal `pull_request_read get` (`mergeable_state`) answers "is CI green / can I merge?" — if `clean`, **merge now**, don't arm a timer. A turn that ends in "waiting" while an actionable state already exists is the bug the operator sees as *"you are stuck."*
- **Agent-completion notifications are not a reliable sole wake signal, and `run_in_background:false` is ignored** (every agent runs detached). A lost notification once idled the loop ~7 h. Background **bash-task** timers are reliable — so a timer is a legitimate **lost-signal backstop**, but a backstop only, never a pacing device and never a substitute for checking durable state. (The operator declined self-heartbeats; the durable-state poll above is the real mechanism.)
- **Subagents can die SILENTLY, and a mid-run relaxation of this rule cost ~1 h idle.** Two agents once died with no completion notification at all. So: **every dispatched agent MUST write its deliverable to a durable path before returning** — a branch/PR for code, a named file for research/reviews/verdicts, stated in the brief as "write it to `<path>` BEFORE returning, so the result survives even if your completion notification is lost." Of the two that died, the one whose deliverable was a PR lost nothing; the one told merely to *return a brief* lost all of its work. **And: never end a turn with an outstanding agent and no armed wake source.** Re-arm the self-terminating watcher whenever ANY agent is outstanding — one watcher covering all of them, e.g. `for i in $(seq 1 N); do [ -f "$A" ] && [ -f "$B" ] && { echo READY; exit 0; }; sleep 45; done; echo "TIMEOUT: ..."`. It fires once on the real signal and exits, and its timeout branch names *which* artifact is missing, so a silent death surfaces as a wake instead of an indefinite idle.
- **Never infer an agent is dead from its harness transcript's mtime — probe first.** The dispatcher once declared a live agent dead on a stale mtime, took over its work, and wrote a false claim about it into a PR body; the agent was mid-rebase the whole time, and its *own* report file was newer than the "last write" the mtime showed. Judge only from the agent's own outputs (pushed commits, its durable report, a PR), compare timestamps across signals, and **`SendMessage` the suspected-dead agent before taking over** — cheap, non-destructive, definitive. Also: "the work is durable" is not "the agent is finished." If you do act on a mistaken inference, **correct the record visibly** rather than deleting it.
- **Interrupts kill detached workers with no durable trace** — so every worker brief opens with **branch-and-push-first** (empty commit + `git push -u` as the first action). And **the WO file is untracked in the main tree, so a fresh worktree won't contain it** — commit the WO first, or copy it into the worker's worktree after spawn (a plain file write; it doesn't interrupt the agent).
- **Context hygiene:** poll CI with `pull_request_read get`/`get_status`, never `actions_list`/`actions_get` — those dump multi-KB repository objects that bloat context on every poll. **Self-terminating backstops:** instead of a fixed `sleep N` timer (which fires stale after the agent already completed), use `until git ls-remote --exit-code origin <branch>` / `until <PR open>` so the backstop fires ONCE on the real signal and self-exits; for a lens/verdict with no git artifact, have it `touch` a sentinel and `until [ -f sentinel ]`; or just `TaskStop` the paired backstop when its completion notification lands. One watcher live at a time; no stale timers.

## Context is disposable between versions — the files are the memory (RUN-005; operator-directed)
The dispatcher's durable memory is the FILES (`STATE.md` boot sector, `FEATURES.md`, the current run report, `DECISIONS.md`, this file, the WOs) — a session boots cold from them. The *conversation* is almost entirely ephemeral: once a milestone merges and its outcome is in the run report, its diffs / PR JSON / screenshots / exit-report notifications are dead weight. So:
- **Delegate heavy reading to subagents; keep only the verdict.** Diffs, screenshots, transcripts, big files → read them in workers/reviewers (ephemeral context), return a compact verdict. The dispatcher rarely reads a diff or screenshot itself.
- **A version boundary is a context-refresh checkpoint.** "Push to v1.0, no stops" means continuous *building*, NOT one unbounded context — a chain of lean per-version sessions satisfies it.
- ⚠️ **The automated fresh-session-per-version handoff via `create_trigger` is NON-VIABLE, and an earlier version of this file prescribed it.** Tried at the v0.5 close: the trigger creates, but **a tool-created trigger stores no MCP connectors, so the fired session runs without `mcp__<server>__*` tools** — and since there is no `gh` CLI here, the entire loop (PRs, reviews, CI, merges) runs on the GitHub MCP tools. A connector-less fresh session is a **toolless dispatcher**. The GitHub connector did not pass through even from a session that holds it; connectors can only be attached by creating or editing the routine from the claude.ai routines UI, which is an operator action. **So: prefer in-session auto-compaction** (automatic, keeps all tools, and the files remain the durable memory either way) — that is the path the v0.6 run took, operator-chosen. A trigger handoff is available only if the operator wires a connector-carrying routine. The context *discipline* below is unaffected and is what actually keeps context bounded.
- The dispatcher cannot self-`/compact` — that is the operator's or the harness's auto-compaction. What it can do is keep the files self-sufficient (run report + STATE, which the cold-start gate already forces), so a compaction or a cold boot loses nothing.

## Two processes, always

`npm run dev` serves the UI and only **enqueues** work. `npm run worker` drains ingest and analysis jobs. Without the worker, uploads sit `queued` forever — the UI now says so instead of showing a calm badge.

## Operator standing directives — these override the habits below

Recorded verbatim-in-substance because they changed how the loop runs, and because earlier guidance in this file contradicted some of them.

- **Max 2–3 concurrent agents; prefer 2.** *"try not to spawn more than 2, max 3 agents at a time."* The dispatcher had peaked at **six**, and the pathologies were all coordination, not throughput: a stale backstop firing against finished work, a review dispatched against a head a parallel rebase had moved, a PR opened on a mistaken liveness inference, and enough notification traffic that the operator twice had to ask what was running. Quality came from **sequencing** (build → independent review → repair → re-review), never from breadth. *When at the cap, stop the out-of-order agents, not the in-order ones — and check for durable artifacts before killing.*
- **Strict version order.** *"please follow the playbook and do things in order, version after version."* Finish and **close** the current version — its close gates and retro included — before any work on the next begins. Read-only recon for version N+1 is not free parallelism: it splits attention, invites work a later decision invalidates, and makes "what version are we on" ambiguous in the record. Research for N+1 is N+1's work.
- **Native iOS is the target, and it is v0.8.** *"I want to do a native app if possible on ios."* So PWA/Capacitor/React-Native alternatives are background context, not live options — evaluate *how to build native well*, not *whether to*. Ladder: **v0.7 = E-39 quality sweep** · **v0.8 = E-40 hosted + E-41 native iOS** (hosting is a prerequisite for a phone app, so they ship together).
- **Every dispatched agent writes its deliverable to a durable file BEFORE returning.** Standard WO/dispatch boilerplate now. A deliverable that exists only as a return value is one that can evaporate — and did.
- **A test that cannot fail is worse than none: demand the mutation proof.** Four instances in v0.6 alone, including the test written to fix the third instance. Every WO asks the worker to break the thing deliberately, show the test failing, restore, and quote the output. An assertion must derive its expectation from **ground truth** (the fixture input), never from the artifact under test — `expect(x).toBe(f(x))` is not a test. Prefer asserting the *positive*: "no A1 lesson" is satisfied by no lesson at all.
- **Never end a turn with an outstanding agent and no armed wake source.** (See the wake discipline above.)
- **v0.7's sweep is a QUALITY sweep, not a ledger tidy-up.** *"money is cool but most important is having extremely high quality product with all features working really well and delivering high quality service, with no bugs."* The tracked debt list is *input*, not the goal. The defects that would have hurt the user in v0.6 were never crashes or failing tests — they were **dead ends and silent wrongness** that passed every gate. So a money defect is reframed as *"the app must not lie about what it costs"*, internal tidiness ranks last, and the gate is behavioural: a cold-start walk plus a deliberate failure-path walk on the built server, with every dead end either fixed or explicitly recorded as accepted.

## How to run the loop (mfactory D-16 — this is new, and it matters)

The previous run was measured at **74% worker time, 100% sequential**; that was the bottleneck, not review.

- **Parallelize milestones that are genuinely independent** — each worker in its own **git worktree**, merges always **serialized**. Required for a batch: no shared contract between them (anything rewriting a shared read-model runs alone); **at most one migration** (versions collide, and a renumber-after-the-fact left a permanently unbootable database this version); **the dispatcher performs the FEATURES/STATE ritual once after the batch merges** — parallel workers must not, or every PR conflicts on those two files; each PR rebased with `gates` re-run before its own merge; and the independence rationale recorded. **Width is capped at 2–3, prefer 2** (operator directive, below) — the earlier "~3–4" is superseded.
- **No diff-line cap.** One milestone, one PR; size follows the milestone. Don't split into a/b — six such splits cost ~2.4 h last run while the cap was exceeded anyway. The per-file 500-line hook is the real guard.
- **Pipeline** — dispatch worker N+1 while review N runs, unless N+1 depends on N's output.
- **Declare a review tier** in every work order: **Full** (never skippable — money/billing, migrations/schema, data deletion, secrets, concurrency/leases, the ingest or analysis correctness path, external contracts), **Light** (timeboxed fidelity + obvious harm), **None** (gates only; the automated gates always run). A worker may **raise** a tier, never lower it.
- **Price findings; don't obey them (D-15).** A BLOCKING verdict is a demonstrated harm handed to you — weigh it against deployment context and either require one repair, accept it as a recorded limitation and merge, or defer it. One repair cycle, then decide. **Never waivable:** real-user-data loss, secret exposure, unrecorded spend.
- **Don't nurse a failing session (mfactory D-17 wave).** Correcting a live session is capped at two attempts per problem; after the second failed correction, kill it and dispatch fresh with an amended brief naming the failure. Infrastructure deaths (spend limit, network) don't count against this — re-dispatch the same brief.
- **Cold-start walkthrough before closing a version (mfactory D-17 wave).** Dispatch a fresh, no-context session: clean clone, only the repo's own written instructions, drive Erika's core promise (upload real speech → reach findings) with one real input, once. Its entire output is `PASS`, or `FAIL` plus the first broken step, quoted. ~20 min, judges nothing else. A FAIL is a defect of the *closing* version — fix before declaring it closed. **It has now justified itself on two consecutive watch versions and is non-negotiable.** At **v0.4** it caught a release blocker (migration v17's asset load 500'd *every* DB route only inside Next's webpack server bundle on a fresh DB — invisible to `npm run test`/`build`, since vitest runs in Node's realm, and to a pre-seeded product-lens run, since migrations are shipped-once). At **v0.6 it FAILED the version and blocked its close**, surfacing three criticals with **967 tests green throughout**: a worker that refused to ingest without an API key so the founding loop never started (and the app's own remedy was a loop), a placement flow that permanently mis-set the curriculum with re-placement unable to repair it, and a database left unbootable by a migration renumber. **Its value is that it is the only check performed the way a user meets the product** — cold, from zero, with nothing configured. Unit suites test units; reviews read diffs; only this asks "can a person actually use this today". Never waive it, and let its failure block a close, as it did. **Its known gaps, both owed:** it is a manual gate, so the cheap automated closure is a **CI smoke-boot of the built server hitting one DB route** (→ E-39); and **CI does not run the 12 Playwright specs the repo already has**, which is exactly why a completely unreachable page shipped this version.
- **The errand lane (`.mfactory/playbooks/errand.md`, new).** A bounded standalone task from the operator — PR triage, a diagnosis, a small fix on a Light/None surface — doesn't need a work order or a dispatcher: one session, strongest model, real verification, full platform gates. It structurally cannot touch a Full-tier surface or exist inside a mission; anything bigger routes to `dispatch.md` as normal.
- **Run reports carry a Signals block now** (`templates/run-report.md`) — sessions, outcomes, routing misses, hook blocks, wall clock/tokens per role, a pass ledger. Fill every row; "n/a" is an answer, blank is not.
- **mfactory's `runs/` is the permanent cross-product archive (mfactory D-17).** Before declaring a mission closed, sync the filed run report back into `mfactory-v2/runs/` and push it there — this is part of filing, not optional housekeeping. It feeds `factory-retro.md`, mfactory's own self-improvement checkpoint (advisory only, operator-ratified — it never edits Erika or itself).

## Verification practices v0.6 proved — three of them, the hard way

These are not general advice; each one is the direct residue of a specific failure this version, and each is cheap.

1. **Drive the built app; don't just read the diff.** E-37's pronunciation studio shipped with **every** route into its drill page returning "That drill is no longer available." — the milestone's entire loop was dead, **958 tests passed**, and **three independent Full reviews had read the branch and could not see it**. The fourth drove a real browser against the built keyless server and found it in minutes. Root cause was a framework asymmetry (Next hands **pages** a percent-encoded route param and **API routes** a decoded one) hidden by a **hand-built test context** that passed the decoded value — a fictional fixture asserting a contract the framework does not implement. Rules: a hand-built framework context is a fictional fixture; where a framework's contract differs between two surfaces, test **both**; every user-facing surface needs at least one test that reaches it the way a user does; and **any Full review of a milestone with a UI includes walking it in a browser**. Reading finds wrong logic; driving finds features that do not exist.
2. **Prove which server answered you.** While verifying the cold-start fixes, a worker started a built server on a common port and its probe actually talked to **a different session's leftover server**, returning plausible, confident, **wrong** answers. It caught this itself and hardened its script. This is the most dangerous failure mode in the whole verification stack: not a test that fails, not even a test that cannot fail, but **a test that passes against the wrong subject** — it looks exactly like success. And since "I drove the built server" is now our most trusted technique, every such claim is only as good as that guarantee. **Rule:** bind an unusual or random port, then **prove the responder is your own build** before trusting one result — assert a string unique to the build, or check the process (`/proc`) — and state the proof in the report. A reviewer who cannot show which server it talked to has not verified anything.
3. **Fix invariants, not instances.** **Five repairs in v0.6 created their own mirror image** — usually the opposite polarity of the same violation: placement seeded sub-level rules so a placed learner isn't handed A1, and the seeding then blocked the DAG so they were offered **zero** grammar; letting the learner record when the rendition fails let them retire a drill **having never heard the correct line**; gating the visit on `heard` made a learner who tried during an unheard lap **never** able to register a visit; keying "today's thread" on capture time still reported the wrong time because `sessions.created_at` is the *upload* instant; and refusing to seed on an untrustworthy response style still **recorded a run**, silently erasing an honest learner's whole placement while the screen said "nothing else has changed". Every one was a correct fix that addressed the *reported instance* and not the *invariant*. Rules: **state the invariant, then enumerate every path that could violate it, before writing the fix**; **ask what the opposite failure looks like**; when a fix branches on an enum, **handle the whole enum**; and note that **the fix's own reasoning is usually the tell** — when a repair articulates a principle, check it against every branch, including the ones it did not touch. Finally, **a claim enforced only by prose will drift**: one of those repairs headlined that copy and writes "cannot drift apart again" with zero tests on the copy, and restoring the exact old false sentence passed 994/994.

Two more from the same version, cheap to keep: **a repair cycle's fixes must be reviewed for their interactions**, not just individually (three collisions in v0.6); and **an operator ruling can invert what the correct fix is** — re-derive the open findings after any ruling.

## Context a cold session cannot infer

- **The dev database is disposable.** Delete `data/` freely; it regenerates. Do **not** do migration archaeology to preserve test rows — that mistake cost a full repair cycle and an escalation.
- **"Shipped" is not a git property, and v0.6 paid for forgetting it.** A migration is shipped once *applied anywhere*, because the runner reads `_migrations` on disk, not git. E-37's migration was applied on its own branch as v24, then renumbered to v26 with no repair step — so every database that had ever booted that branch threw on **every** boot, forever, and three source comments asserted v24 "never shipped". `lib/migrations/reconcile.ts` now runs before the migration loop and repairs that ledger row. Amend-before-merge is only safe while every database holding it is disposable, and **migrations are not intrinsically idempotent** — every `up` is a bare `CREATE`/`ALTER` except the v17/v18 seeds, and the `_migrations` ledger is the sole idempotency, which is why this was fatal rather than a no-op (owed → E-39).
- **Code drifts from this project's own research.** Two v0.6 money defects were already documented *correctly*, with citations, in `docs/research/` before the wrong constant was written — and nothing compared them. When a WO cites a researched constant, diff it against the repo's research docs before writing it, and reconcile any mismatch explicitly. **Pin safety-critical constants as bounds, not equalities** (`rates.ts` now asserts floors, plus the structural invariant that a cached rate can never exceed the uncached rate it discounts) and **name the dangerous direction at the definition** — for spend, over-estimating costs a slightly early refusal; under-estimating makes the cap a lie. Also: **a review that flags one instance is not a sweep** — the reviewer caught one under-priced row; the fix agent found another 3× worse in the same table.
- **Fixtures prove mechanism, not judgment (D-13).** Where a criterion pins a threshold or parses another system's output, demand a real *labelled* sample or an explicit "uncalibrated" note plus truthful degradation. Two production bugs reached the operator through fixtures built to be easy.
- **A real test can still assert the wrong contract (D-14).** Two shipped tests encoded defects *as* the contract and ~20 reviews passed them. Read assertions as specifications — especially any test a diff changed or deleted; this reading now applies at every review tier, including Light.
- **Verify against disposable state, always (`task.md`, generalized from the lesson below).** Throwaway paths, temp databases, sandboxed config — never the product's default data path, a real account, or a live external side effect unless the work order says so.
- **Encoded, formerly OPEN — now CLOSED:** verification runs targeting the product's default data path (`data/erika.db` — an agent did, and pushed an unmerged migration onto the operator's real database) and the missing "new user, clean checkout, reaches findings" path are both covered — the first by the disposable-state rule above, the second by the cold-start walkthrough. The old note here said to *watch one version* before treating the walkthrough as closed for good. **Two watch versions have now answered it:** v0.4 (a release blocker) and v0.6 (three criticals, and the gate failed the version). Treat it as closed and load-bearing.
